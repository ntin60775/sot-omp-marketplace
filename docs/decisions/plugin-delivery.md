# ADR: доставка плагинами (принята 2026-09-11)

## Контекст

Прежняя схема — каталог и дом разработки в одном репозитории, плагин отдаётся
относительным путём (`./plugins/ontoship`), догфуд-копия собирается
`scripts/sync-package.sh` — не пережила столкновения с реальностью.

Инвентаризация восьми 1С-проектов показала цену копирования:

- одна поставка размножилась в четыре поколения: 18 правил в `erp-main`,
  9 в `erp-mini`, 5 в `retail`, 3 в `zupupr`;
- линтер BSL (`1c-bsl-code-style` вместе с его скриптом и справочниками)
  разошёлся **во всех восьми** — восемь версий исполняемой проверки, и какая
  из них правильная, не определено ничем;
- в четырёх проектах хуков нет вообще — детерминированные гейты там не работают;
- за сутки наблюдения живой проект обогнал эталон на четыре файла: копирование
  не удерживает синхронность даже при дисциплине.

## Решение

### 1. Три дома, разные по природе

| Уровень | Дом | Доставка |
|---|---|---|
| машина | `sot-omp-core` (приватный) | `sync.sh` → `~/.omp/agent/` |
| проект | репозитории плагинов | `omp plugin install --scope project` |
| каталог | этот репозиторий | `omp plugin marketplace add` |

Машинный слой плагином ехать **не может**: `RULES.md` (sticky identity),
`WATCHDOG.md`, `TITLE_SYSTEM.md` и `config.yml` читает только native-провайдер
из каталога агента — слотов под них в структуре плагина нет. Отсюда скрипт.

### 2. Репозиторий на плагин, источник — с закреплённым `ref`

Относительный источник (`./plugins/x`) не пинится ничем: установка берёт
содержимое из клона каталога, то есть HEAD ветки. Две машины, поставившие плагин
в разные недели, получают разные правила, и «у нас одинаково» не гарантируется
ничем. Поэтому каждый плагин живёт в своём репозитории, а запись каталога
ссылается на тег.

### 3. Приватные репозитории подключаются SSH-URL

Установщик клонирует по HTTPS. Для приватного репозитория это даёт
`Repository not found. Authentication failed`, если не настроен credential
helper. Источник вида `{ "source": "url", "url": "git@github.com:…" }`
работает без правки глобального git-конфига. Проверено на обоих плагинах.

### 4. Установка — в проект, не в машину

1С-контур и KB принадлежат проекту: у них есть контекст (база, учётка, состав
расширений) и своя версия, которую проект вправе приморозить. Цена решения:
ворктри не наследуют `.omp/plugins/` — шаг установки плагинов добавляется в
`tasks/init-worktree.sh` проекта.

### 5. Раскладка плагина — корень репозитория либо подкаталог

- обычный плагин — содержимое в корне (`rules/`, `skills/`, `extensions/`,
  `package.json` с `omp.extensions` для TS-хуков);
- omp-native репозиторий — `git-subdir` + `path: ".omp"`: корнем плагина
  становится сам пакет, и генерируемая догфуд-копия со sync-скриптом не нужна.

### 6. Имя `RULES.md` в плагине не используется

Native-провайдер (приоритет 100) всегда перекрывает плагинный (90), поэтому файл
с таким именем не загрузится никогда. Платформенные блоки лежат под собственным
именем с `alwaysApply: true`.

### 7. Зависимостей в каталоге нет

Схема каталога не знает поля `dependencies`. Связка «плагин `1c` требует
`unica@unica`» обеспечивается навыком развёртывания, а не механизмом.

## Следствия

- `plugins/` и `scripts/sync-package.sh` в этом репозитории — наследие прежней
  схемы: вторая копия OntoShip рядом с его настоящим домом (`ontoship-omp`).
  Подлежат удалению.
- Разработка плагинов ведётся в их собственных репозиториях, а не здесь.
- Прежний канал — копирование `.omp/` руками — уходит.

## Статус
