# Контракт: инструмент не врёт о состоянии поставки

> **Прогрилено 2026-09-18, два раунда.** Политика: оба проектных sticky-файла
> уходят из `REQUIRED_IGNORES`. Объём: инструмент и политика — **разными
> срезами** (два тикета). Материализация: **жёсткий** вид `materialization` и для
> проектного, и для user-scope корня, включая **отсутствующую** запись. Версии
> каталога: `unversioned` — **мягкий** вид, такие плагины в ожидаемый состав не
> вносятся. Git-флоу: ветка → MR в `main`, **стоп после MR**.

## Goal

Три места, где `consumers.py` расходится с диском, закрыты: гейт краснеет там,
где поставка действительно не работает (плагин зарегистрирован, а payload
недоступен), не краснеет из-за плагинов, которые нельзя проверить, и не требует
от проектов игнорировать их собственные файлы.

## Done

- `check` знает **жёсткий** вид `materialization`: мёртвый `installPath`, битый
  симлинк в `node_modules`, отсутствующая запись у наблюдаемого плагина — и в
  проектном корне, и в user-scope.
- `unversioned` — **мягкий** вид (каталог знает плагин, но версии не объявил);
  жёсткий `unknown` остаётся за «каталог плагина не знает». `discover --apply`
  такие плагины в `plugins[]` не вносит и сообщает причину.
- `.omp/RULES.md` и `.omp/APPEND_SYSTEM.md` перенесены из «игнорируется» в
  «версионируется» — в константе инструмента и в каноническом блоке, одним
  изменением (тест сверки константы с документом зелёный).
- `python3 -m pytest tests/` зелёный; `gitmark lint` зелёный.
- На живой машине: `check` зелёный на `erp-demo` **без правок в проекте**, новые
  виды не дают ложных срабатываний ни у одного из 12 потребителей.

## Scope

- `scripts/consumers.py`, `tests/test_consumers.py`,
  `docs/reference/consumer-repo-layout.md`, `docs/reference/consumer-registry.md`
  (описание новых видов дрейфа).
- Схема реестра (`schemas/consumer-registry.schema.json`) не меняется: виды дрейфа
  — значения отчёта, а не поля реестра.

## Constraints

- **Git-флоу этого репозитория — только `main`** (ветки `dev` нет). Ран:
  `git worktree` → ветка `fix/consumers-drift-fidelity` → push → **MR в `main`**;
  **стоп-точка — после MR** (дефолт `stop-before-commit` не применять).
- Один срез = один тикет; порядок `01` → `02`.
- Поставку потребителей не трогать: `.omp/` и `.gitignore` двенадцати проектов —
  не предмет этого рана (тикет 02 закрывает `erp-demo` правкой **политики**, а не
  проекта).
- Тесты — часть тикета, не «потом»: `python3 -m pytest tests/`.

## Context

Инцидент 2026-09-17 (раздача `1c` 0.1.3 → 0.1.4 → 0.1.5 по семи проектам) вскрыл
все три расхождения; два обхода уже описаны в
[upgrade-consumers](../../ops/upgrade-consumers.md) §6, а сами факты — в тикетах.
Коротко:

- `retail` стоял с битым симлинком `node_modules/unica → …/unica___unica___0.11.0`
  (кэш снесён первым апгрейдом), а `check` показывал `✓ чисто` — он читает реестр
  маркетплейса, а не материализацию.
- `discover --apply` для `project-bp` внёс в ожидаемый состав
  `redaktura-skills@redaktura-skills` — глобальный навык из чужого каталога без
  объявленной версии; запись пришлось снимать руками, иначе `check` красный.
- `erp-demo` красный на `gitignore` из-за `.omp/APPEND_SYSTEM.md`, где лежит
  «Роль проекта»: omp читает этот файл из `<cwd>/.omp/` (project-first), а
  политика требует его игнорировать как машинный слой, который на самом деле
  живёт в `~/.omp/agent/`.
