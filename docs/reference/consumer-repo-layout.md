# Раскладка репозитория-потребителя

Одно правило: **доставленное не версионируется, своё — версионируется.** Всё, что
приходит плагинами каталога или машинным слоем, живёт в своих репозиториях; копия в
проекте — это вторая правда, которая расходится с первой (ровно тот дрейф, от которого
уходим, см. [решение о поставке](../decisions/plugin-delivery.md)).

## Что игнорируется

| Путь | Почему |
|---|---|
| `.omp/plugins/` | состояние установки и `node_modules` — машинное, воспроизводится `omp plugin install` |
| `.omp/skills/`, `.omp/commands/`, `.omp/scripts/` | payload плагинов: источник истины — их репозитории, версия пинится записью каталога |
| `.omp/mcp.json` | локальная конфигурация MCP (порты, пути машины) |
| `.omp/.backup-*` | локальные бэкапы перед снятием копий |
| `.gitmark/`, `*-map.html` | производное KB — пересобирается `gitmark index` / `map` из markdown |
| `.scratch/`, `.artifacts/` | локальные рабочие артефакты агента |

## Что версионируется

| Путь | Почему |
|---|---|
| `.omp/rules/` | **свои** правила проекта — под именами, не совпадающими с плагинными (ADR §6). После снятия копий здесь только своё |
| `.omp/RULES.md`, `.omp/APPEND_SYSTEM.md` | **проектные** файлы omp: он читает их из `<cwd>/.omp/` (project-first), поэтому «Роль проекта» и правила проекта живут здесь. Машинный слой (`sot-omp-core`) в проекты не пишет — он в `~/.omp/agent/`. **Оговорка:** копия *плагинного* правила под этими именами — по-прежнему вторая правда, но инструмент её не поймает: gitignore-проверка смотрит пути, а `migrate` классифицирует только файлы под `.omp/{skills,rules,commands,scripts,extensions}` — эти два лежат прямо в `.omp/`. Такое знание ловится ревью |
| `.omp/extensions/` | проектные расширения-хуки. **Кроме файлов под плагинными именами**: плагин `1c` доставляет свои хуки (`unica-gate.ts`, `doc-gate.ts`, `retry-gate.ts`), и копия под тем же именем перекрывает плагинную (нативный провайдер, 100 против 90) — это дрейф `legacy`, а не своё знание |
| `.omp/TECH_DEBT.md`, `.omp/unica-gate-escalations.txt` | решения и разрешённые исключения проекта |
| `.omp/skills/<свой>/`, `.omp/commands/<своя>.md` | если проект заводит собственные навыки/команды — force-add (`git add -f`) |
| `AGENTS.md`, `docs/`, `tasks/`, `src/`, `tests/`, `features/`, `fixtures/`, `tools/` | содержимое проекта |

## Ссылки на доставленное

Из той же границы следует политика ссылок: **KB-ссылка указывает только на то, что
версионируется в этом же репозитории.** Доставленное (плагины, машинный слой) в
репозитории не лежит — значит, целью ссылки быть не может.

| Что нужно | Как |
|---|---|
| Связь между документами KB | обычная markdown-ссылка или `links:` — путь внутри репозитория |
| Упоминание пакетного артефакта («правило `kb-first` приезжает плагином `ontoship`») | текстом; путь — инлайн-кодом или в код-блоке, **не ссылкой** |
| Исполнимая команда в runbook или тикете | путь в установленный плагин `.omp/plugins/node_modules/<плагин>/…` — внутри код-блока |
| Ссылка, которая должна читаться вне этой машины | URL в репозиторий-источник (внешняя ссылка: I4 её пропускает) |

**Почему не ссылкой на `.omp/plugins/…`.** В рабочем дереве такая ссылка резолвится
(плагин установлен), но в свежем клоне до `omp plugin install` она битая — линт краснеет;
`omp plugin uninstall` ломает её снова; граф KB её не видит, потому что цели нет в
множестве версионируемых `.md`. Вердикт I4 становится функцией состояния машины — ровно
тот класс дефектов, от которого уходим. Замер 2026-09-19 (движок 0.4.7, изолированные
репозитории-модели):

| Вариант | Линт на машине | Свежий клон | Ребро графа | `consumers.py` |
|---|---|---|---|---|
| путь в установленный плагин | OK | **ERR** | — | чисто |
| проза без ссылки | OK | чисто | — | чисто |
| URL в источник | OK | чисто | — | чисто |
| симлинк под плагинным именем | OK | **ERR** | есть | дрейф `legacy` |

**Почему не симлинком.** Симлинк под плагинным именем (`.omp/rules/kb-first.md` → файл
пакета) инструмент классифицирует как `shadowing` — «файл, чей путь есть в поставленном
пакете: перекрывает плагинное правило и подлежит снятию». Файл под плагинным именем —
вторая правда, независимо от того, копия это или ссылка (проверено на живом
потребителе). Симлинк под неплагинным именем инструмент терпит (`project_own`), но он
покупает только лишний файл и ту же машинную зависимость.

**Архивные тикеты.** Их ссылки на снятые пути — историческая запись, и переписывать
содержимое не нужно. Но мёртвая ссылка из frontmatter снимается: гейт `lint` требует
0 ERR, а историю хранит текст, а не битый путь.

## Канонический блок для `.gitignore`

```gitignore
# --- omp: поставка плагинами (каталог sot-omp-marketplace) ---
# Доставленное не версионируется здесь: источник истины — репозитории плагинов и
# машинный слой (sot-omp-core). В проекте версионируется только своё:
# .omp/rules/ (имена не совпадают с плагинными), .omp/extensions/,
# .omp/RULES.md и .omp/APPEND_SYSTEM.md (их omp читает как проектные),
# .omp/TECH_DEBT.md, .omp/unica-gate-escalations.txt.
.omp/plugins/
.omp/skills/
.omp/commands/
.omp/scripts/
.omp/mcp.json
.omp/.backup-*

# Производное KB (пересобирается из markdown) и локальные артефакты
.gitmark/
*-map.html
.scratch/
.artifacts/
```

Осторожно с огульным `.omp/`: он закрывает и `.omp/rules/`, а значит **потеряет свои
правила проекта** при клоне — вместе с проектными `.omp/RULES.md` и
`.omp/APPEND_SYSTEM.md`, если они есть. Если в репозитории стоит именно `.omp/`,
замените его на блок выше и добавьте свои файлы (`git add -f .omp/rules/…`).

Для репозитория без собственных правил под `.omp/` огульная строка корректна и
проверку проходит: сам каталог `sot-omp-marketplace` держит именно её. Предупреждение
выше — про проекты, у которых в `.omp/rules/` лежит своё.

## Блок проверяется инструментом

`python3 scripts/consumers.py check` даёт по этому блоку вид дрейфа `gitignore` и
перечисляет незакрытые строки (в `--json` — полем `ignores`). Сверяется смысл, а не
символы: шаблон закрывает требуемый путь, если накрывает сам путь или любой его
каталог-предок. `*` и `?` не переходят через `/`, `**` переходит — как их читает git.
Поэтому `.omp/` и `.omp/*` закрывают всё под `.omp/`, а `/.gitmark/` и `.gitmark`
равны `.gitmark/`.

Отмена (`!`) в проверке не участвует: она делает путь версионируемым, а это решение
проекта о своём — свои `rules/skills/commands` по политике живут в git. Раскладка
«`.omp/*` плюс `!` для своих каталогов» проверку проходит: инструмент не судит о том,
что проект держит у себя, он проверяет, что политика применена и пути закрыты.

Набор требуемых строк инструмент держит константой, а тест сверяет её с блоком выше:
политика и код не могут разъехаться молча. Правка политики — это правка блока здесь,
и больше ничего.

## Переходный случай: копии уже в git

До поставки копии пакета могли быть закоммичены (так было в `erp-main`, `retail`,
`subvost-xray-tun`, `rusbread-master-site`). После `migrate --apply` они удаляются из
рабочего дерева — это **трекаемые удаления**, их надо закоммитить вместе с новым
`.gitignore`, иначе репозиторий останется в полу-состоянии: файлы в индексе есть, на
диске их нет.

Проверить состояние потребителя целиком: `python3 scripts/consumers.py check`
(дрейф, свои файлы, хук ворктри) и `verify` (индекс, `deploy-check`, версия движка).

> **Оговорка на 2026-09-15.** Часть правил этого блока движок GitMark пока не
> понимает: правило с `/` без хвостового слэша (`.omp/.backup-*`, `.omp/mcp.json`)
> теряется молча, а шаблон каталога с путём (`.omp/skills/`,
> `.omp/commands/`) не матчится никогда. Для git эти файлы игнорируются, для индекса
> KB — нет: пока правка не выпущена, каталоги бэкапов и копий могут попадать в
> `gitmark search`. Симптом, обход и проверка — gotcha
> `ontoship-omp/docs/ops/gotcha-gitignore-rules-with-path.md`, правка — план
> `gitignore-parser.md` в том же репозитории.
